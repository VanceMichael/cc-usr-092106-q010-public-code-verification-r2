# 公众扫码来源核验后台设计规约

> 适用域：`public-code-verification`（与 `contracts/context.schema.json` 的 `domain` 标识一致）。
> 本文件约定发布规则、隐私边界、缓存失效、异常输入处理、异议轨道、订阅通知与历史留痕；
> `contracts/verification-result.schema.json`、`contracts/query-error.schema.json`
> 是本规约对外契约的机器可读版本。所有样例均为虚构数据。

## 1. 设计目标与不可让步项

日均数百万、峰值扫码场景下，公众只需要一个可解释的结论：**手中这盒药来源是否可信**。
由此推出四条硬约束：

1. **只发布可解释状态**：每个状态都必须附带发布理由与数据截止时间，禁止"裸结论"。
2. **最小知情**：前一位购药人身份、具体就诊/购药机构、侦办案件信息永不进入公众响应；
   轨迹节点只展示类型 + 粗粒度地域 + 时间 + 必要摘要。
3. **权威轨迹只追加、不受公众输入影响**：公众异议走独立工单轨道，只有权威方发出的
   更正/风险事件才能改变状态。
4. **结论可回溯**：任意历史时刻页面上给出的旧结论，事后都能还原"当时依据哪一版规则、
   哪一版数据、因为什么理由给出"。

## 2. 状态模型与发布规则

公众查询只返回以下五种互斥状态（枚举值 `states`）：

| 状态 | 标识 | 发布条件（必须全部满足） | 公众语义 |
|---|---|---|---|
| 生产可溯 | `PRODUCED` | 权威库存在该码的生产/出厂记录；生产主体资质有效；无未消解的阻断事件 | "来源可追溯，为正规生产产品" |
| 合法流转 | `LEGIT_CIRCULATION` | 满足 `PRODUCED` 条件，且最近一条权威流转环节类型属于合法流通/经营/使用环节，链路连续无断点 | "正在合法流通环节中" |
| 已召回 | `RECALLED` | 权威方发布了覆盖该码所属批次的、生效中的召回事件 | "该批次已被召回，请勿使用，按召回指引处理" |
| 待复核 | `PENDING_REVIEW` | 存在权威库登记但证据未闭合：如链路断点、环节资质待核、权威方主动挂起复核 | "信息正在复核中，暂不能确认" |
| 无法确认 | `UNCONFIRMED` | 码格式合法但权威库无登记，或上游权威数据暂不可用且无可用缓存 | "系统无法确认该码，请通过其他渠道核对" |

发布规则要点：

- **状态由规则引擎对"权威事件流 + 规则版本"计算得出**，不由人工在运营后台直接手改。
  人工动作（立案、抽检）必须落成事件，再由规则生效。
- 每个响应必须带：`state`、`reasons[]`（机器可读理由码）、`rule_version`、
  `data_as_of`（所用权威快照时间）、`generated_at`、`result_ref`（本次结论的不可变引用）。
- `reasons` 至少 1 条；理由码是有限枚举（如 `manufacturer_record_found`、
  `chain_continuous`、`recall_active`、`chain_gap_detected`、`code_not_registered`、
  `upstream_unavailable`），公众文案由前端按理由码 + 语种渲染，后端不拼接自然语言。
- `RECALLED` 响应必须携带召回行动指引编号（`notice_ref`）与公众可执行动作
  （停用、联系退货渠道），但不含执法细节。
- **异地短时扫码不是降级依据**。同一追溯码短时间内在多地被扫，只作为风控观测信号
  （可能是代购转运、设备时间错误、码被拍照传播，也可能是被仿冒），
  **绝不单独把状态降为 `PENDING_REVIEW` 或 `UNCONFIRMED`**。
  只有该信号与权威侧异常（环节断点、主体资质异常、鉴定结论）合流时，才按规则复核。
  规则：`scan_geo_anomaly` 可作为 `PENDING_REVIEW` 的*伴随*理由，不得作为*唯一*理由。
- 内部风控标签（"疑似串货""调查中""重点关注"）不进入公众响应字段，
  仅在权威事件流中驱动状态机。

## 3. 隐私分级与节点摘要

公众响应中的轨迹（`trail[]`）逐字段白名单化：

| 权威库内部字段 | 公众响应 |
|---|---|
| 生产企业名称 | 仅当企业为公示主体时展示；否则展示主体类型 + 省级地域 |
| 经营/配送企业 | 环节类型（"批发流通""零售终端"）+ 省级地域，**不展示机构名** |
| 医疗机构名称 | **永不展示**；至多"某省医疗机构"粗粒度摘要 |
| 购药人/患者身份、医保标识、联系方式 | **永不展示、不入日志关联输出** |
| 案件编号、办案单位、侦查状态 | **永不展示**；召回等结论只引用对外公告编号 |
| 时间 | 精确到日；时分秒仅内部保留 |
| 批号 | 展示（本身印在包装上，非个人信息） |

契约层强制：`trail[].node` 只允许 `node_type`、`region`、`at`、`summary` 四个键；
校验器对 `patient`、`institution_name`、`case_id` 等禁词键直接拒绝发布
（见 `src/verification.py`）。响应整体走 DTO 白名单序列化，禁止内部实体直出。

日志同样遵守：访问日志只留 `code_hash`（HMAC-SHA256，密钥按周轮换）、粗粒度地域、
状态码与理由码，不留明文码与身份联合视图。

## 4. 查询接口与输入处理矩阵

`GET /v1/verify?code=…`（扫码）与 `POST /v1/verify:batch`（离线补查）为全部读入口。
各类输入处理刻意区分：

| 情形 | 判定 | 处理 |
|---|---|---|
| 重复扫码 | 同码 + 同设备/会话在去重窗口（如 60 秒）内重复请求 | **幂等**：返回同一 `result_ref`，不重复计入风控、不产生新通知；正常走缓存 |
| 离线补查 | 客户端登录后批量重放扫码记录 | 按**当前**权威状态返回（不按扫码历史时刻复活旧结论）；每条结果带 `generated_at`；批量接口独立配额；扫码端本地时间只作排序，不参与状态计算 |
| 恶意枚举 | 单位时间内大量格式合法但命中率低的查询、IP/设备异常 | 分层限速：软限速要求人机验证，硬限速返回 `429 RATE_LIMITED`；错误响应时延、字节数与正常响应对齐，避免时序侧信道；封禁只影响访问，不影响结果 |
| 码不存在 | **格式合法、权威库无登记** | 正常 200 响应，状态 `UNCONFIRMED` + `code_not_registered`；与"查得到"走同样延迟预算，不暴露注册元数据（不说是何时、何地登记的） |
| 残损输入 | 校验位错误、长度不符、字符集非法、解码失败 | `400 MALFORMED_INPUT`（见查询错误契约），提示重新扫码或手工录入；**不查权威库、不产生查询事件、不计入枚举信号**，避免脏输入污染风控 |
| 上游不可用 | 权威数据源熔断且无缓存 | `UNCONFIRMED` + `upstream_unavailable`（对公众统一为"暂时无法确认"，但理由码区分，便于监测），严禁伪装成"无此码"或"来源可信" |

关键区分：**残损输入在入口拒绝，码不存在在权威侧确认后给结论**，两者响应码、
是否计入风控、是否消耗权威库配额都不同。

## 5. 缓存与精确失效

### 5.1 缓存结构

- 键：`verify:{code_hash}`；值中带 `rule_version` 与权威数据 `epoch`。
  规则版本发布即换键空间，避免新旧规则结论串用。
- 正结论（`PRODUCED`/`LEGIT_CIRCULATION`）短 TTL（建议 60–300 秒）；
  `RECALLED`/`PENDING_REVIEW` TTL 更短或订阅失效广播；
  `UNCONFIRMED` 短 TTL（建议 30–60 秒），防止权威补录后长期误报。
- 负缓存（无登记码）同样短 TTL，并与枚举限速共享计数但语义分离。
- 边缘节点与应用本地缓存只缓存可公开的结论 DTO，**永不缓存内部轨迹实体**。

### 5.2 失效触发（只精确失效，不全量冲刷）

权威侧两类事件驱动失效：

1. **权威更正事件（`authority.correction`）**：按事件影响范围携带
   `code` / `batch_id` / `manufacturer_lot` 标签。缓存维护码→批次的倒排索引，
   召回、批次风险升级时按批次一次性失效该批全部码。
2. **风险升级事件（`risk.escalated`）**：如批次从正常变为召回/复核，
   除失效缓存外，同步驱动第 7 节的订阅通知。

失效通道：事件总线 → 缓存失效服务 → 各缓存层（集中式 Redis、应用本地、CDN  surrogate）
按标签清除；失效本身幂等并带事件版本号，乱序到达时以版本号判定新旧，
**旧事件不能把新结论冲掉**。失效处理有对账任务：周期性比对缓存条目与权威 epoch，
发现漏失效立即补删并告警。

## 6. 异议与受控证据（独立轨道）

公众可对结论提交异议（`POST /v1/disputes`）：

- 异议工单是**独立事实源**，任何字段都不写入权威轨迹库，不直接改变状态。
- 证据受控：允许类型（照片、视频、票据图片）、大小/数量上限、服务端杀毒与脱敏扫描、
  加密存储、固定保留期后删除；提交人只能回看自己的工单。
- 工单流转给核查机构；**只有权威核查方在权威系统中签发更正/风险事件后**，
  状态才按第 2、5 节规则变化。工单中存该事件引用，形成闭环但方向单一。
- 提交人收到的每个工单状态都引用查询时的 `result_ref`，便于第 8 节回溯。

## 7. 订阅与风险通知

- 订阅必须**明确主动发起**（扫码结果页二次确认，带撤回入口）；无静默订阅、
  不从扫码行为自动开通。订阅粒度为码或批次，带订阅时确认的结论版本。
- 触发条件：权威事件导致该批次**风险结论变化**（如正常→召回、召回范围扩大/缩小）。
- 发送前即时重算收件人集合，只发给同时满足以下全部条件的订阅者：
  1. 订阅仍有效（未撤回、未过期）；
  2. 其订阅的码/批次**仍被本次结论覆盖**（批次范围缩小时排除不再受影响的人）；
  3. 未就同一事件版本收到过通知（事件版本去重，幂等发送）。
- 通知内容最小化：状态变化、生效批次、公众行动指引编号、查询链接；
  不含病历、机构、案件信息。
- 降级通知与升级通知对称处理（解除召回也要通知），避免旧风险信息长期误导。

## 8. 历史结论留痕（为什么当时给出旧结果）

- 权威侧事件流与规则版本均只追加；每次发布的结论写一条**不可变发布记录**：
  `result_ref → {code_hash, state, reasons, rule_version, data_epoch, generated_at}`。
- 公众响应携带 `result_ref`；页面可长期凭它回看"该次结论当时的依据"
  （数据快照版本 + 规则版本 + 理由码），即使最新结论已改变。
- 订阅通知与异议工单均引用 `result_ref` / 事件版本。
- 更正发生后，新页面展示新结论 + "信息已于 X 更新"的说明入口；
  旧结论不被抹除，满足审计与申诉需要，也避免"页面昨天说可信今天说召回却无解释"。

## 9. 高可用与降级

- 查询层无状态、多可用区部署；权威轨迹库以只读副本 + 快照对外服务，
  权威系统故障不阻断查询。
- 熔断与降级次序：命中缓存（即使刚过期，按"陈旧可接受"配置返回并附
  `stale` 与 `data_as_of` 标识）→ 权威只读快照 → 均不可用时
  `UNCONFIRMED/upstream_unavailable`。**任何降级都不得输出确定性的可信结论。**
- 峰值保护：边缘缓存吸收重复扫码；批量补查走独立通道与排队；
  事件总线、通知发送、缓存失效全部异步化并可重放。
- 可观测性：按状态、理由码、输入类别、缓存命中/失效版本、通知实发人数分维度监控；
  "状态翻转率""失效延迟""订阅误发（发给不受影响者）"为零容忍告警指标。

## 10. 组件与数据流（逻辑视图）

```
扫码端 ──► 接入/限流/输入校验 ──► 查询服务(无状态)
                                   │  ├─ 缓存层(Redis/本地/CDN) ◄── 失效服务 ◄─ 事件总线
                                   │  └─ 权威只读快照/副本
                                                          ▲
权威系统(生产/流转/召回/资质) ──事件流(只追加)───────────┘
                                   ├─ 规则引擎(版本化) ── 发布记录(不可变)
                                   ├─ 异议工单服务(独立库 + 受控证据)
                                   └─ 订阅通知服务(发送前重算受影响集合)
```

## 11. 版本约定

- 对外契约字段变更遵循 `schema_version` 整数递增（与领域资料的 `version` 约定一致）。
- 规则变更发布 `rule_version`；新旧版本可并行，缓存按版本隔离。
- 状态枚举、理由码、错误码只增不删语义；废弃走弃用期，不得复用旧码表达新含义。
